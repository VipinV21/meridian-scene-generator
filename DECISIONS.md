# Design Decisions and Epistemic Architecture

The core problem is preserving epistemic isolation: a language model handed the full story text will confidently write a character who knows things they never witnessed. The architecture rests on one governing choice: the model that writes the scene never sees the raw story. It only sees a pre-filtered knowledge state for one character at one point in time.

## Story Representation and Rejected Alternatives

The story is represented as a structured event ledger across six episodes. Each event records who directly observed it, who was informed afterward, who partially witnessed it without full context, and what secrets it produced. From this, a second layer computes, for any character at any story point, three sets: allowed knowledge, suspicions and misconceptions, and forbidden knowledge — facts they have no way of knowing.

Two alternatives were rejected. Retrieval-augmented generation over story chunks doesn't track who-knows-what: a query about Kamala and Dev would retrieve Dev's Hyderabad deal on relevance grounds even though Kamala never witnessed it — vector search has no concept of an observer boundary. A system prompt with the full story and an instruction to "pretend" a character only knows certain things was also rejected: that's a soft constraint beside the facts it's supposed to withhold, and models leak past soft constraints when forbidden information is present in context regardless of instruction.

## Where the Constraint Is Actually Enforced

The constraint is enforced structurally, before generation, not by instruction alone. The pipeline never assembles a prompt containing the full story — it filters the ledger to one character's allowed knowledge and suspicions, and only that filtered set goes into the model's context. Forbidden knowledge is deliberately kept out of the generation prompt entirely, not passed as a "don't mention this" list: if a fact is never in the context window, the model cannot leak it by accident, and a negative list would undercut that guarantee by putting the withheld facts back in front of the model. Forbidden knowledge is used only downstream, by the verifier, to check the output after the fact.

When an API key is configured, the filtered prompt goes to OpenAI GPT-4o, Gemini, or Groq's Llama 3.3 (checked in that priority order) for live generation. Without a key, the six assessment cases fall back to pre-written scenes so the project runs end-to-end with no external dependency, and any other combination returns an explicit placeholder rather than a scene pretending to have been generated. Every response states which path produced it.

## Verification and Its Limits

Verification runs in three layers. The first is hand-written regex, precise but specific to the six assessment cases. The second pulls distinctive words out of each forbidden-knowledge item and flags likely leaks by keyword co-occurrence — works for any character or point, but is lexical, not semantic: it can miss a leak that never uses the forbidden fact's own vocabulary (a scene where "Wren suddenly understood why the theatre wouldn't be there next year" reveals the building sale without saying "sale" or "building"), and can false-positive on coincidental overlap. The third layer sends the scene and the character's forbidden-fact list to whichever model is configured and asks it to judge, fact by fact, whether the scene reveals or implies it — catching the paraphrase case the first two structurally cannot. This layer only runs when a key is configured; without one, verification proceeds on the first two, and the response reports plainly that the semantic check was skipped rather than implying it ran.

This isn't hypothetical: one of the six curated fallback scenes originally had Wren recall watching Kamala lock the grant file away — invented for atmosphere, but contradicting the ledger (Kamala did that alone), and neither lexical layer caught it, since the sentence shared no vocabulary with the forbidden item's wording. A human read caught it, not the automated check — exactly the gap the third layer is meant to close without needing another manual read.

## When There Is Very Little to Draw On

For a character with a thin observation history at a given point, the allowed-knowledge list is simply short. Rather than inventing plot events to fill the gap, the prompt has the model lean on atmosphere, setting, and the character's few genuine memories; silence is preferred over fabrication.

## A Genuine Weakness

Two things worth naming honestly. First, the ledger is hand-built for six episodes; a longer serial would need automated extraction, with a human checking the model's proposed observer-tagged events rather than writing them from scratch. Second: an earlier version special-cased the six assessment prompts, returning a hand-tuned knowledge split instead of deriving it from the ledger. That made the graded cases look right without proving the representation could produce that result on its own. The fix: delete that lookup table, route all six through the same ledger-derived path as any untested input, and add two small layers — character-specific inference (conclusions drawn from already-witnessed facts, not a fact anyone told the character) and per-character private knowledge (a thought one observer doesn't share with others at the same event). A related bug surfaced later: one event bundled three facts of different reach into a single summary — Priya's public introduction as stage manager, Tomas privately arranging her hire, and the two of them being related — with every read-through attendee marked as an observer of the whole thing. That handed the private facts to everyone in the room as allowed knowledge, bypassing the verifier entirely since they were never forbidden in the first place; splitting it into three separately-scoped events fixed it, and it's now a regression test. The curated fallback scenes still exist for when no key is configured, and read more polished than live generation typically produces — a real gap, worth naming.
